## What the Auditor Checks

The auditor verifies AVS configuration and Azure-services integration evidence across **at least 3** of the listed capabilities, supported by **at least 2** documentation artifacts.

**Typical questions:**
- Which 3+ integration capabilities have you implemented? Show each.
- Where are the architecture diagrams covering networking, HA/DR, backup, management, monitoring, and load balancing?

## Evidence Guidance

### Azure Blob backend for Content Library

- Configure vSphere Content Library on AVS to use an Azure Blob container as backend
- Screenshot of Content Library configuration referencing the blob URL

### Identity source

For AVS, two patterns are common:
1. **On-prem AD reachable from AVS** via ExpressRoute (ER) / VPN — vCenter Single Sign-On (SSO) bound to on-prem AD
2. **Domain controllers on Azure VMs** (federated with on-prem AD) — vCenter SSO bound to the Azure-hosted DCs

Document chosen pattern + AVS SSO configuration.

### Add / remove hosts without app impact

- Show the procedure (vCenter DRS evacuation + host removal)
- Reference a real instance (change ticket + before/after host count)

### Public Internet on AVS

Two options:
- **NSX-T DNAT** for inbound + SNAT for outbound
- **Azure-managed Public IP** consumed via the AVS Public IP service

### Quota-increase process

- Document the process: AVS portal → Quota request → support ticket
- Provide an example: requested 4 → 6 node quota, approved on date

### Virtual WAN multi-site

- Virtual WAN hub with AVS ExpressRoute circuit attached
- Multiple branches / regions attached
- Routing intent / routing policies if used

## Common Gaps

- **Only 2 capabilities covered**: V1.9.1 requires **at least 3**. Pick easy wins (identity, Content Library, scale).
- **Identity source unclear**: vCenter SSO binding to AD must be explicit — screenshot the SSO config.
- **Diagrams don't cover all 5 areas**: Networking / HA/DR / Backup / Mgmt+Monitoring / Load Balancing must all be represented.
