## Azure Monitor Alert Rules

Create each alert in **Azure Portal → Monitor → Alerts → Create → Alert rule** and target the AVS private cloud, connected Log Analytics workspace, or paired ExpressRoute circuit. Record the alert ID, action group, and runbook link in the operations repository.

| Alert name | Severity | Metric or signal | Threshold | Window |
|---|---|---|---|---|
| AVS vSAN Capacity Warning | Sev 3 | vSAN capacity utilisation | > 70% used | 15 minutes |
| AVS vSAN Capacity Critical | Sev 1 | vSAN capacity utilisation | > 85% used | 15 minutes |
| AVS Host CPU Sustained High | Sev 2 | Host CPU usage | > 85% average | 15 minutes |
| ExpressRoute Utilisation High | Sev 2 | ExpressRoute bandwidth | > 80% of committed bandwidth | 15 minutes |
| Defender for Cloud Unhealthy AVS Guests | Sev 2 | Defender for Cloud unhealthy resources | > 0 unhealthy virtual machines | 5 minutes |
| NSX-T Configuration Sync Failure | Sev 2 | NSX-T Manager sync status / admin event | Any failure event | Immediate |
| AVS Host Health Degraded | Sev 1 | Host health state | Degraded or unavailable | 5 minutes |

### Immediate response procedures and escalation paths

#### AVS vSAN Capacity Warning / Critical

1. Open **Azure Portal → Azure VMware Solution → Private clouds → Storage** and confirm current usage and datastore trend.
2. In vCenter, identify the top consumers and check for snapshots, failed backups, or orphaned disks.
3. For the warning threshold, initiate clean-up or workload placement review within the same business day.
4. For the critical threshold, raise a Sev 1 incident, pause non-essential migrations, and prepare node expansion.
5. Escalate to the AVS platform owner immediately; if projected exhaustion is within 24 hours, open Microsoft support and notify the customer service owner.

#### AVS Host CPU Sustained High

1. Open **Azure Monitor → Metrics** for the private cloud and verify the 15-minute trend.
2. Cross-check host utilisation in vCenter and identify noisy VMs, backup jobs, or HCX activity.
3. Pause non-essential HCX waves or maintenance jobs.
4. Rebalance workloads with DRS or scale out the cluster if the saturation is structural.
5. Escalate to the cloud engineer first; escalate to the solution architect if scaling or reservation changes are required.

#### ExpressRoute Utilisation High

1. Validate the metric against the ExpressRoute circuit in **Azure Portal → ExpressRoute circuits → Metrics**.
2. Confirm whether traffic is migration-related, backup-related, or production workload related.
3. Rate-limit HCX or replication traffic if it is consuming migration bandwidth.
4. If business traffic is affected, execute the agreed fallback plan such as VPN failover for non-critical flows.
5. Escalate to the network lead and open a provider ticket if the circuit or provider edge is unstable.

#### Defender for Cloud Unhealthy AVS Guests

1. Open **Defender for Cloud → Recommendations** and list the unhealthy AVS guest VMs.
2. Confirm whether the issue is missing agent deployment, missing plan assignment, or a genuine security exposure.
3. Restore the agent or plan assignment first; if the VM is genuinely vulnerable, create a remediation ticket with the workload owner.
4. Track the finding until the unhealthy count returns to zero.
5. Escalate to the security operations lead for all unresolved critical findings.

#### NSX-T Configuration Sync Failure

1. Open NSX-T Manager and confirm the failed sync object, edge, or policy area.
2. Check recent changes, pending publishes, and failed service insertions.
3. Retry sync only after confirming no conflicting change window is active.
4. If the failure affects routing, firewall, or public exposure, freeze further changes and declare a Sev 2 incident.
5. Escalate to the network engineer and engage Microsoft support if the sync fault persists.

#### AVS Host Health Degraded

1. Validate the degraded state in **Azure VMware Solution → Private clouds → Hosts** and in vCenter.
2. Check whether workloads have already evacuated and whether vSAN is resynchronising.
3. Stop non-essential maintenance and migration actions.
4. Open Microsoft support immediately if a host is unavailable or repeatedly flapping.
5. Escalate to the AVS platform owner and customer incident manager.

## Incident Response Procedures

| Severity | Response SLA | Initial actions | Escalation path |
|---|---|---|---|
| Severity 1 (Critical) | 15 minutes | Declare incident, validate business impact, freeze change activity, engage customer bridge, open Microsoft support at highest severity, and start executive updates. | Operations engineer → AVS platform owner → customer incident manager → Microsoft support → VMware engineering through Microsoft. |
| Severity 2 (High) | 1 hour | Confirm affected service, start technical triage, assign incident owner, capture logs and metrics, communicate workaround if available. | Operations engineer → cloud or network lead → solution architect → Microsoft support if platform issue suspected. |
| Severity 3 (Medium) | 4 hours | Log ticket, assess scope, schedule remediation or workaround, update backlog and customer status report. | Operations engineer → service owner; escalate to cloud engineer if configuration change is needed. |
| Severity 4 (Low) | Next business day | Record issue, prioritise in backlog, review during daily or weekly operations stand-up. | Operations engineer → project or service manager as needed. |

## Action Guides

### Host Failure Response

1. Detect the failed or degraded host in Azure Portal and vCenter.
2. Confirm DRS evacuation status and check whether workloads restarted elsewhere.
3. Verify vSAN resynchronisation health and estimated completion.
4. Notify Microsoft support and attach screenshots, timestamps, and affected cluster details.
5. Track host recovery, capacity risk, and any workload exceptions until the cluster returns to green.

### vSAN Storage Capacity Critical

1. Validate datastore usage and recent growth trend.
2. Identify large snapshots, stale backups, ISO files, or unexpected replication bursts.
3. Remove safe-to-delete objects and confirm free space recovery.
4. If capacity remains above 85%, raise a node-expansion action and obtain customer approval.
5. Verify that backup jobs, monitoring dashboards, and the capacity report reflect the new state.

### ExpressRoute Flap or Disconnection

1. Validate circuit alarms, BGP state, and branch impact.
2. Confirm whether Azure service health or provider maintenance explains the flap.
3. Fail over approved traffic to VPN if the customer design supports it.
4. Notify the network provider and Microsoft support, then communicate business impact to stakeholders.
5. When stable, verify routing convergence, private-endpoint resolution, and application reachability.

### NSX-T Edge Failure

1. Open NSX-T Manager and inspect edge-node health, alarms, and route advertisements.
2. Validate BGP session state and northbound route presence.
3. Restart or redeploy the impacted edge service only within the approved runbook.
4. Re-test north-south traffic, load balancing, and DNS forwarding.
5. Record the incident in the change log and update the resilience backlog if additional hardening is needed.

## 30 / 60 / 90-Day Milestones

| Milestone | Deliverables | Success criteria |
|---|---|---|
| Day 30 | Daily incident review, alert-threshold tuning log, first restore test, migration-defect list closed or assigned | No unresolved Severity 1 incidents, core alerts routed correctly, restore proof captured |
| Day 60 | Performance review, backup validation report, Defender for Cloud posture review, updated optimisation backlog | Backup and security posture validated, priority performance issues remediated or accepted |
| Day 90 | Capacity-planning report, reservation or scaling recommendation, final hypercare exit review, ownership handoff | Customer accepts steady-state support model, optimisation backlog prioritised, hypercare formally closed |

## Hypercare Exit Checklist

- [ ] Alert owners and escalation contacts confirmed.
- [ ] All Severity 1 and Severity 2 incidents resolved or transferred with ownership.
- [ ] Restore and disaster-recovery evidence filed.
- [ ] Monthly optimisation backlog agreed with the customer.
- [ ] Hypercare exit approval recorded in the project log.
