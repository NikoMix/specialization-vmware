These six patterns cover the vast majority of AVS engagements. Each section provides a target topology, NSX-T design, ExpressRoute and Global Reach design, identity, backup, monitoring, and an indicative cost envelope.

<Aside type="tip">
  Pick the closest pattern at design time and document the deltas in the architecture document. That
  is usually enough to prove alignment to Azure Architecture Center guidance for control A.2.2.
</Aside>

---

## 1. Datacenter exit / rehost (HCX bulk)

**When:** Customer is exiting one or more datacenters, a vSphere refresh is due, and minimal application change is preferred.

| Element | Design choice |
|---|---|
| AVS topology | Single AVS private cloud, single cluster, AV36 / AV52 / AV64 based on sizing |
| Migration | HCX bulk migration with mobility groups; Network Extension for IP retention |
| Network | ExpressRoute plus Global Reach to on-premises during migration; optional cut to AVS-only post migration |
| NSX-T | T0 upstream, T1 per workload tier, distributed firewall deny-all plus allowlist |
| Identity | On-premises Active Directory reachable via ExpressRoute; vCenter single sign-on bound to Active Directory |
| Backup | Azure Backup Server or partner equivalent for guest VMs |
| Disaster recovery | Optional second cluster in AVS or out-of-region target |
| Cost envelope | Reservation for steady state; pay-as-you-go for migration surge |

---

## 2. Stretched cluster (active/passive metro)

**When:** Mission-critical workload needs zero or near-zero recovery point objective across availability zones.

| Element | Design choice |
|---|---|
| AVS topology | Stretched cluster across two availability zones in the same region |
| Storage | vSAN Express Storage Architecture with stretched-cluster policy |
| Network | Latency and bandwidth tested between zones; redundant ExpressRoute |
| NSX-T | T0 active/active; distributed firewall consistent across both sides |
| Identity | Same as pattern 1 |
| Backup | Backup platform aligned to the stretched-cluster service tier |
| Disaster recovery | Built in via stretched cluster; second region optional |
| Cost envelope | Higher due to duplicated capacity across zones |

---

## 3. DR-to-AVS (on-premises primary, AVS as DR)

**When:** Customer keeps on-premises as the primary site and modernises the disaster-recovery target.

| Element | Design choice |
|---|---|
| AVS topology | Smaller AVS private cloud sized for disaster-recovery steady state plus failover headroom |
| Replication | HCX DR or SRM with vSphere Replication |
| Network | ExpressRoute plus Global Reach; replication bandwidth sized to the recovery-point objective |
| NSX-T | Mirrors the on-premises segment plan |
| Identity | Same Active Directory as on-premises |
| Backup | Existing customer backup with AVS guest protection added for failover state |
| Disaster recovery | The pattern itself |
| Cost envelope | Lower steady state, surge during actual failover |

---

## 4. VDI adjacency (Horizon on AVS)

**When:** Customer runs Horizon VDI and wants Azure adjacency for AI, data, or managed services.

| Element | Design choice |
|---|---|
| AVS topology | Dedicated cluster sized for Horizon density |
| Horizon | Horizon on AVS with profile tooling such as App Volumes or FSLogix |
| Network | ExpressRoute plus Global Reach; egress sized for end-user traffic |
| NSX-T | Distributed firewall micro-segmentation per pod |
| Identity | Same Active Directory as on-premises; conditional access through Entra ID |
| Backup | Profile and user-data backup strategy |
| Disaster recovery | Cross-region Horizon failover if required |
| Cost envelope | AV36P or AV52 for VDI density |

---

## 5. Hybrid steady-state (Arc + AVS + selective burst)

**When:** Customer keeps most VMware on-premises and uses AVS only for selected workloads that need Azure adjacency.

| Element | Design choice |
|---|---|
| On-premises | Azure Arc-enabled VMware vSphere resource model |
| AVS | Small AVS footprint for selected workloads |
| Network | ExpressRoute plus Global Reach |
| NSX-T | Standard distributed firewall baseline |
| Identity | Shared Active Directory and Entra ID posture |
| Backup | Common backup tooling across on-premises and AVS |
| Disaster recovery | Per workload; AVS can be the DR target for selected services |
| Cost envelope | Smallest AVS footprint with strong governance value from Arc |

---

## 6. Mission-critical app rehost (Oracle, SQL FCI, large SAP non-prod)

**When:** Customer has VMware-dependent workloads that cannot move directly to standard Azure infrastructure-as-a-service.

| Element | Design choice |
|---|---|
| AVS topology | Dedicated cluster, often AV52 or AV64 for memory-heavy workloads |
| Workload | Oracle RAC, SQL FCI, SAP, or other VMware-bound applications |
| Storage | Azure NetApp Files for AVS datastores at Premium or Ultra tier |
| Network | ExpressRoute plus Global Reach; latency-sensitive paths explicitly designed |
| NSX-T | Micro-segmentation by application tier |
| Identity | Application-specific identity and secret-management dependencies |
| Backup | App-aware backup such as RMAN or SQL-native tooling |
| Disaster recovery | Active/passive or stretched cluster |
| Cost envelope | Higher due to premium node and storage choices |

---

## How to choose

| Customer signal | Recommended pattern |
|---|---|
| Datacenter exit | 1 |
| Near-zero recovery-point objective mandate | 2 |
| Disaster-recovery modernisation | 3 |
| Horizon VDI estate | 4 |
| Vast majority of workloads stay on-premises | 5 |
| Oracle, SQL FCI, or SAP blocked from hyperscale IaaS | 6 |

> Most engagements combine multiple patterns, for example pattern 1 plus pattern 3 for exit and disaster recovery. Document every in-scope pattern in the architecture document.
