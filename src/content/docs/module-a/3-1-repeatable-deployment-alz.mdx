## What the Auditor Checks

The auditor verifies adherence to **Azure Landing Zone design areas** via **repeatable Infrastructure-as-Code**. The deployment must configure at minimum: **Identity** (Entra ID or equivalent), **Networking topology** (including hybrid via ExpressRoute / VPN Gateway), and **Resource organization** (tagging + naming). One of four approaches is accepted: (1) Start small, (2) Full ALZ conceptual, (3) Alternative articulated, (4) Brownfield update.

**Typical questions:**
- Show the IaC repository — which tool: Bicep, Terraform, or ARM? *(Pick one per V1.9.1 Dec 1, 2025 clarification — not all three.)*
- Walk us through the ALZ conceptual architecture you aligned to, or the ALZ Accelerator you used.
- Where is the Azure Landing Zone Review confirming multi-region or multi-zone redundancy policy?

## Evidence Guidance

### IaC repository

- Git repo with the IaC source, README, and a deployment guide
- Pipeline definition (GitHub Actions / Azure DevOps) demonstrating the deployment is automated
- Tagging + naming standards enforced via Azure Policy

### Identity

For AVS specifically, the AVS private cloud authenticates via vCenter local accounts (cloudadmin) but the customer's Azure tenant must show Entra ID with conditional access, PIM where appropriate, and any federation with on-prem AD.

### Networking topology

For AVS:
- Hub-and-spoke or Virtual WAN hub
- ExpressRoute circuit (customer ER + AVS managed ER) with Global Reach where applicable
- NSX-T segments for AVS workload networks
- Non-overlapping CIDRs across on-prem / AVS management / AVS workload

### Azure Landing Zone Review

- Run via Microsoft Assessments
- Export results
- Confirm policy assignments for multi-region or multi-zone redundancy

## Common Gaps

- **Showing Bicep + Terraform + ARM "to cover bases"**: The Dec 1, 2025 clarification is explicit — choose one tool per customer.
- **No Azure Landing Zone Review on file**: The Review is mandatory for confirming the redundancy policy posture.
- **CIDR overlap with on-prem**: Common AVS gap — networking design must show non-overlapping ranges across on-prem, AVS management, and AVS workload networks.
- **Identity only documented as "we use Entra"**: Show the conditional-access policies, PIM, and any federation explicitly.
