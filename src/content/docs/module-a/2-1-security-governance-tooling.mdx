## What the Auditor Checks

The auditor verifies that you have the capability to **deploy governance and security tooling for compliance and security baselines**, demonstrated through both an operational tool deployment and a completed Microsoft Cloud Adoption Security Review.

**Typical questions:**
- Show the security baseline deployed for two customers (Defender for Cloud, Sentinel, or an equivalent 3rd-party stack).
- Where is the completed Cloud Adoption Security Review for each customer?
- How are the findings tracked through to remediation?

## Evidence Guidance

### Defender for Cloud (or 3rd-party) baseline

For AVS specifically:
- **Defender for Servers** on AVS guest VMs (covered also in B.4.2)
- **Defender for Cloud** secure score for the AVS subscription
- **Sentinel** workspace consuming AVS syslog (NSX-T, vCenter, ESXi)

If using a 3rd-party stack, include vendor naming + scope and explain coverage parity.

### Cloud Adoption Security Review

- Run via the [Microsoft Cloud Adoption Security Review](https://learn.microsoft.com/security/) assessment
- Export results
- Map findings to the customer's remediation backlog

### Governance tools

- Azure Policy assignments at MG / Sub scope (ALZ-aligned)
- RBAC baseline (custom roles for AVS operators, NSX admins)
- Naming + tagging standards enforced via policy

## Common Gaps

- **No Cloud Adoption Security Review on file**: It is required — without it the control fails.
- **3rd-party tool with no scope mapping**: If you don't use Defender for Cloud, you must explicitly map your 3rd-party coverage to the equivalent Microsoft security baselines.
- **AVS guest VMs missing from Defender for Servers**: Common AVS-specific gap — make sure the guest OS coverage extends into the AVS private cloud.
